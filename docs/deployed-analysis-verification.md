# 배포 환경의 소식 분석·제안 반영 검증

공개 API에서 소식 저장 → 분석 → 제안 조회 → 소유자 반영 → 항목·근거·이력·현황판 조회를 확인하는 절차다. 격리 DB·가짜 제공자 기반 자동 테스트, 배포 성공, 실제 모델의 출력 품질은 별도로 기록한다. 특정 실행의 결과는 이슈·PR에 남기고 이 문서에는 재사용할 절차만 유지한다.

## 실행 범위

- 로그인 계정, 전용 검증 공간, 합성 소식, 허용 분석 횟수와 반영 대상을 먼저 정한다. 기본 예시는 공간 1개·소식 1건·분석 최대 1회·소유자 CREATE 제안 1건이다. 실제 모델 호출에는 비용이 발생한다.
- 구분 가능한 합성 데이터를 사용하고 로그인은 사용자가 브라우저에서 직접 완료한다. 기존 가족의 업무 원문·공간을 검증 대상으로 사용하지 않는다.
- 쿠키·비밀번호·CSRF·검토 토큰·AI 내부 키·실제 업무 원문을 저장소·이슈·PR·스크린샷에 기록하지 않는다. OpenAI 키는 AI에만 둔다.
- 생성한 검증 자료의 정리 범위는 별도로 정한다. 검증을 위해 기존 데이터나 DB를 초기화하지 않는다.

## 배포·인증 사전 점검

1. 최신 dev SHA와 같은 SHA의 `Backend CI`·`Deploy backend` 결과를 확인한다. health UP이어도 이전 릴리스일 수 있으므로 필요한 Swagger 작업의 존재를 함께 확인한다.
2. CI/CD의 실패 단계와 원인을 구분한다. 이미지 빌드 중 Gradle 다운로드 HTTP 504처럼 일시적인 외부 장애라면 로그·동일 SHA·현재 dev를 확인한 뒤 실패 작업과 후속 작업을 재실행한다. 테스트·체크섬·권한·시작 실패를 같은 원인으로 취급하지 않는다. dev가 바뀌면 배포의 최신 커밋 보호 절차를 따른다.
3. `GET /actuator/health`·`/v3/api-docs`를 읽는다. 공간 생성, 소식 저장·분석 상태 조회, 제안 상세·반영, 항목·근거·이력·현황판 조회 작업을 확인한다.
4. 로그인한 같은 브라우저 프로필로 `https://api.hanmaum.site/swagger-ui/index.html`을 연다. `GET /api/users/me`의 200 확인 후 `GET /api/auth/csrf`의 토큰을 Swagger `CsrfToken` 인증 입력에 연결한다. HttpOnly 세션 쿠키는 브라우저가 보내며 직접 복사하지 않는다.
5. 워커 설정의 활성화 여부를 확인한다. GitHub Variables의 `ANALYSIS_WORKER_ENABLED=true`는 배포 입력이며 실제 적용은 성공한 릴리스의 설정과 실행 결과로 확인한다. 전체 환경 파일을 출력하지 않는다. 설정·타임아웃은 [워커 배포 안내](deployment.md)의 활성화·비활성화 절차를 따른다.

## 합성 시나리오

예시 원문은 `검증 전용 합성 소식입니다. 2026년 11월 10일 오전 10시에 한마음 검증센터 방문 예약이 있어요.`다. 실행 전 날짜·시각·장소와 기대하는 제안 유형을 확정하고 모델 결과에 맞춰 기대값을 바꾸지 않는다. 실제 예약이나 돌봄 지시가 아니다.

| 순서 | 요청·작업 | 확인할 결과 |
| --- | --- | --- |
| 1 | `POST /api/spaces`에 검증 호칭과 새 `clientRequestId` 제출 | 201, `spaceId`·본인 `membershipId`, 소유자 역할 확보 |
| 2 | 공간의 항목·제안·현황판 조회 | 기존 항목과 혼동하지 않도록 초기 빈 상태 확인 |
| 3 | `POST /api/spaces/{spaceId}/source-records`에 합성 `content`와 별도 `clientRequestId` 제출 | 201, `recordId`·`analysis.analysisId`, 저장 원문 일치 |
| 4 | `GET /api/spaces/{spaceId}/source-records/{recordId}/analyses/{analysisId}`를 제한된 시간 동안 조회 | 최종 COMPLETED, `proposalIds`·처리 시각 확인. 빠른 처리는 QUEUED/RUNNING을 관찰하지 못할 수 있음 |
| 5 | 해당 소식의 제안 목록과 선택 제안 상세 조회 | 원래 `recordId`·`analysisId`, 검토 대기 상태, 원문 근거, 예상 유형·날짜·시각·장소 비교 |
| 6 | 소유자가 `POST /api/spaces/{spaceId}/proposal-applications` 호출 | 200, `batchId` 및 반영 `itemId`·문자열 `itemVersion` 확보 |
| 7 | 소식·제안·항목 목록/상세·근거·이력·현황판 재조회 | 반영 결정과 같은 항목 ID·버전·확정 값·원문 근거, 초기 반영 이력, 날짜에 맞는 현황판 구간 확인 |

분석 완료만으로 항목이 확정되지 않는다. 소유자 반영 전에 확정 항목·현황판에 결과가 생기지 않는지도 확인한다. 제안 0개는 계약상 정상 응답일 수 있으나 위 일정 시나리오의 반영까지 검증한 것으로 기록하지 않는다. 제안이 없거나 다른 유형·불명확한 값만 있으면 그 사실을 기록하고 정해진 호출 한도에서 중단한다.

## 소유자 CREATE 반영 입력

공간 생성·소식 작성과 다른 `clientRequestId`를 사용한다. 상세의 `proposalId`, `action`, 현재 `reviewToken`을 사용하고 `values`는 승인한 최종 검토값으로 구성한다. 제안과 다른 유형이나 작업으로 바꾸지 않는다.

```json
{
  "clientRequestId": "<반영 작업 전용 UUID>",
  "entries": [{
    "proposalId": "<상세 조회한 제안 ID>",
    "action": "CREATE_ITEM",
    "reviewToken": "<상세의 현재 검토 토큰>",
    "values": {
      "itemType": "SCHEDULE",
      "title": "검증센터 방문 예약",
      "description": null,
      "fields": {
        "scheduledDate": "2026-11-10",
        "scheduledTime": "10:00",
        "location": "한마음 검증센터"
      }
    }
  }]
}
```

ID·토큰은 자리표시자다. CREATE에는 기존 항목 버전·잠금을 넣지 않는다. UPDATE/RESOLVE/LINK_EVIDENCE는 별도 시나리오로 현재 항목 버전·본인 잠금·근거와 허용 변경분을 확인한다. 상세 계약은 [제안 반영](proposal-decisions.md)을 따른다.

## 재전송·중단·결과 기록

- 쓰기 응답이 유실되면 같은 작업·같은 `clientRequestId`·같은 본문을 유지해 결과를 확인한다. 새 ID로 다시 만들지 않는다. 분석 상태 GET은 추가 분석 요청이 아니다.
- 허용 횟수에 도달하면 새 소식이나 분석 재시도 API를 호출하지 않는다. FAILED이면 실패 코드를 기록한다. QUEUED가 계속되면 워커 적용 상태, RUNNING이면 lease·AI 호출 상태를 확인하며 무조건 재접수하지 않는다.
- INVALIDATED 제안이나 버전·잠금·현재 참여 변경으로 반영이 거절되면 원인을 확인한다. 과거 검토 토큰이나 바뀐 요청 의도로 우회하지 않는다.
- 실행 SHA, 단계별 HTTP/공개 상태 코드, 검증 자원의 ID 또는 별칭, 기대값과 실제 값, 분석 접수 횟수, 미수행 범위를 이슈·PR에 기록한다. 전체 인증 응답은 복사하지 않는다.
- 소유자 단일 흐름의 결과를 구성원 승인·다중 계정 격리·모든 제안 유형·FE 전체 화면 검증으로 확대하지 않는다. 추가 계정이나 호출이 필요한 범위는 별도로 실행한다.
