# 한마음 백엔드 설계 기준

## 서비스 범위

기획서의 Must Have를 MVP 기준으로 삼습니다. 원본 소식에서 일정·할 일·확인사항·관찰·안내를 제안하고, 사용자가 확정한 내용으로 현재 상태를 갱신합니다.

## 역할 분담

- Spring: 인증, 공간 접근 권한, 원본 저장, 해당 공간의 기존 후보 조회, 제안 저장, 사용자 확정, 트랜잭션, 현재 상태와 변경 이력, 현황판·공유 데이터
- FastAPI: 자연어 항목 추출, 기존 후보와의 관계 판단, 추가·변경·해소 제안 및 근거 반환
- FastAPI는 서비스 DB에 직접 변경을 적용하지 않습니다. Spring은 LLM 호출 중 DB 트랜잭션을 유지하지 않습니다.

## 공간 권한

권한은 계정 전체가 아닌 돌봄 공간 구성원 관계에 저장합니다.

| 작업 | OWNER | MEMBER |
| --- | --- | --- |
| 현재 참여 공간의 소식·항목·근거·이력 조회 | 가능 | 가능 |
| 소식 작성·AI 제안 검토·가족 초대 | 가능 | 가능 |
| AI 제안 반영·항목 등록·수정·담당자 변경·일반 삭제 | 최종 반영 | 변경 요청 |
| 할 일 진행 상태 변경 | 모든 할 일 | 본인 담당은 직접, 나머지는 요청 |
| 질문 답변 제출 | 가능 | 가능 |
| 답변 확인·질문 해소·공간 정보 수정 | 최종 반영 | 변경 요청 |
| 소식 원본 삭제 | 공간 내 모든 원본 | 본인 원본 |
| 구성원 내보내기 | 가능 | 불가 |
| 돌봄 공간 전체 삭제 | 가능 | 불가 |

모든 조회·변경·공유·AI 후보 조회에서 현재 참여 상태와 대상별 권한을 확인합니다. 초대 링크는 발급 후 24시간 유효하며 별도 가입 승인은 없습니다. 이미 참여한 사용자는 중복 참여시키지 않습니다.

소유권은 현재 구성원 한 명에게 원자적으로 이전하고 기존 소유자는 구성원이 됩니다. 공간마다 소유자 한 명을 유지합니다. 소유자는 소유권 이전 또는 공간 삭제 후 나가기·탈퇴가 가능합니다. 참여 종료 시 미완료 담당 할 일은 미지정으로 전환하고 완료 상태·공동 기록·이력은 유지합니다. 위 정책의 도메인 구현은 후속 작업입니다.

## 데이터 변경 원칙

1. 원본 소식과 AI 제안, 확정된 관리 항목을 구분합니다.
2. AI 제안의 대상 ID·근거·생성 시점 버전을 보존합니다.
3. 확정할 때 현재 구성원 권한과 현재 항목 버전을 다시 검사합니다.
4. 선택한 제안 전체를 검증하고 현재 항목 변경·이력 기록·제안 적용·성공 처리 기록을 함께 확정합니다. 한 항목이라도 충돌하면 전체 미반영하며 선택하지 않은 제안은 검토 대기로 유지합니다.
5. 같은 제안의 재확정은 중복 적용하지 않습니다. 다른 가족이 항목을 변경했다면 다시 확인받습니다.
6. 모호한 연결은 후보를 사용자에게 보여줍니다. AI가 언급되지 않은 사실을 확정하지 않습니다.
7. 백엔드가 검증한 허용 필드만 변경합니다. AI의 `changes`를 엔티티에 그대로 복사하지 않습니다.
8. 잠금 단위는 관리 항목 한 개입니다. 잠금 보유는 승인 권한이 아니며 최종 반영 시 권한·버전·잠금을 다시 검사합니다. TTL·갱신 주기 등은 미정입니다.
9. 일반 항목 삭제는 삭제 표시·이력을 보존합니다. 원본 삭제는 원문과 그 내용을 복사한 제안·근거·현재 값·이력 등의 파생 내용을 제거합니다. 연결 해제만으로 끝내거나 소유자 승인 대기로 미루지 않습니다.
10. 독립된 유효 근거가 사라진 항목은 소유자 재확인 전 현황판·새 공유 대상에서 제외합니다. 늦은 AI 결과·이전 편집·반복 요청으로 삭제 내용이 다시 노출되지 않도록 검사합니다.

## 도메인 패키지 계획

루트는 `com.hanmaum.backend`입니다. 도메인 바로 아래 필요한 `controller`, `service`, `repository`, `entity`, `dto`를 추가합니다. 기존 패키지는 이 구조와 맞으므로 이름만 바꾸기 위한 이동은 하지 않습니다.

| 패키지 | 책임 | 현재 상태 |
| --- | --- | --- |
| `auth` | 로그인·로그아웃·CSRF의 HTTP 계약 | CSRF Controller 존재, 로그인·로그아웃은 Security 필터 처리 |
| `user` | 서비스 회원·소셜 계정 매핑·탈퇴 | 예정 |
| `carespace` | 공간·참여·초대·소유권 | 예정, 초대는 이 도메인에 포함 |
| `record` | 원본 소식 작성·조회·삭제 | 예정 |
| `analysis` | 분석 실행·상태·재시도 관리 | 예정 |
| `proposal` | AI 제안·구성원 변경 요청·최종 반영 | 예정 |
| `careitem` | 다섯 항목 유형·잠금·근거·이력 | 예정 |
| `dashboard` | 현재 유효한 항목의 현황 조회 | 예정 |
| `sharing` | 공유 링크·현재 접근 권한 확인 | 예정 |
| `ai` | 내부 FastAPI 클라이언트·설정·DTO | 기존 통신 어댑터 유지 |
| `global` | 공통 설정·보안·응답·예외 | 기존 기반 확장 |

`Common`은 API 명세의 공통 분류입니다. 반복 요청 결과 조회의 실제 패키지와 저장 구조는 해당 기능 구현 시 정하며 빈 Controller나 테이블은 만들지 않습니다.

- Controller는 Service를 호출하고 엔티티 대신 공개 DTO를 반환합니다. 공개 API는 `/api` 기준이며 `/api/v1`로 임의 변경하지 않습니다.
- Service는 업무 규칙·트랜잭션, Repository는 해당 도메인의 영속성 접근을 담당합니다.
- 도메인 간 업무 접근은 Service 경계를 사용합니다. 다른 도메인의 Controller 호출이나 무분별한 Repository 공유를 피합니다.
- 공개 `analysis` 업무는 `ai` 어댑터를 호출합니다. 내부 DTO의 수치 제한·버전 타입을 공개 API 정책으로 그대로 사용하지 않습니다.
- `global.response`는 업무 도메인에 의존하지 않습니다. 전역 예외 처리에서 내부 AI 실패를 공개 오류로 변환하는 기존 경계는 유지합니다.
- 공개 응답은 [API 공통 규격](api-conventions.md), 내부 계약은 [AI 계약](ai-contract.md)을 따릅니다.

ERD와 노션 API는 검토 가능한 초안이며 물리 스키마·업무 구현 완료를 뜻하지 않습니다. 현재 Flyway V1에는 세션 테이블만 있습니다. 입력 제한·페이지네이션·잠금 TTL·검토/삭제 확인값 구현은 해당 기능 전에 합의합니다.

## 운영 기준

- 개발: 로컬 Java·Python 프로세스와 Docker PostgreSQL
- 초기 배포: 외부 LLM API를 사용하는 소규모 MVP, Lightsail Linux 2 vCPU·4GB급에서 시작
- Nginx를 통해 동일 도메인·HTTPS 제공, Spring·AI·DB 내부 통신
- 운영 DB 비밀값은 환경변수로 주입하고 DB 백업은 별도 저장소에 보관
- 단일 서버 장애 시 전체 서비스가 중단될 수 있으므로 실제 이용 규모에 맞춰 DB·애플리케이션 분리 검토
- 합성 기록으로 먼저 검증하고, 실제 부모님 정보를 사용하기 전 동의·열람 범위·공유 내용·데이터 보관 정책 구체화

Redis, 벡터 DB, Spring AI, 메시지 브로커는 초기 의존성에 포함하지 않습니다. 실제 요구와 측정 결과에 따라 도입합니다.
