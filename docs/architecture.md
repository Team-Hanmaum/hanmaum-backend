# 한마음 백엔드 설계 기준

## 서비스 범위

기획서의 Must Have를 MVP 기준으로 삼습니다. 원본 소식에서 일정·할 일·확인사항·관찰·안내를 제안하고, 사용자가 확정한 내용으로 현재 상태를 갱신합니다.

## 역할 분담

- Spring: 인증, 공간 접근 권한, 원본 저장, 해당 공간의 기존 후보 조회, 제안 저장, 사용자 확정, 트랜잭션, 현재 상태와 변경 이력, 현황판·공유 데이터
- FastAPI: 자연어 항목 추출, 기존 후보와의 관계 판단, 추가·변경·해소 제안 및 근거 반환
- FastAPI는 서비스 DB에 직접 변경을 적용하지 않습니다. Spring은 LLM 호출 중 DB 트랜잭션을 유지하지 않습니다.

## 공간 권한

권한은 계정 전체가 아닌 돌봄 공간 구성원 관계에 저장합니다.

| 작업 | OWNER | MEMBER |
| --- | --- | --- |
| 현재 참여 공간의 소식·항목·근거·이력 조회 | 가능 | 가능 |
| 소식 작성·AI 제안 검토·가족 초대 | 가능 | 가능 |
| AI 제안 반영·항목 등록·수정·담당자 변경·일반 삭제 | 최종 반영 | 변경 요청 |
| 할 일 진행 상태 변경 | 모든 할 일 | 본인 담당은 직접, 나머지는 요청 |
| 질문 답변 제출 | 가능 | 가능 |
| 답변 확인·질문 해소·공간 정보 수정 | 최종 반영 | 변경 요청 |
| 소식 원본 삭제 | 공간 내 모든 원본 | 본인 원본 |
| 구성원 내보내기 | 가능 | 불가 |
| 돌봄 공간 전체 삭제 | 가능 | 불가 |

모든 조회·변경·공유·AI 후보 조회에서 현재 참여 상태와 대상별 권한을 확인합니다. 초대 링크는 발급 후 24시간 유효하며 별도 가입 승인은 없습니다. 이미 참여한 사용자는 중복 참여시키지 않습니다.

소유권은 현재 구성원 한 명에게 원자적으로 이전하고 기존 소유자는 구성원이 됩니다. 공간마다 소유자 한 명을 유지합니다. 소유자는 소유권 이전 또는 공간 삭제 후 나가기·탈퇴가 가능합니다. 참여 종료 시 미완료 담당 할 일은 미지정으로 전환하고 완료 상태·공동 기록·이력은 유지합니다. 위 정책의 도메인 구현은 후속 작업입니다.

## 데이터 변경 원칙

1. 원본 소식과 AI 제안, 확정된 관리 항목을 구분합니다.
2. AI 제안의 대상 ID·근거·생성 시점 버전을 보존합니다.
3. 확정할 때 현재 구성원 권한과 현재 항목 버전을 다시 검사합니다.
4. 선택한 제안 전체를 검증하고 현재 항목 변경·이력 기록·제안 적용·성공 처리 기록을 함께 확정합니다. 한 항목이라도 충돌하면 전체 미반영하며 선택하지 않은 제안은 검토 대기로 유지합니다.
5. 같은 제안의 재확정은 중복 적용하지 않습니다. 다른 가족이 항목을 변경했다면 다시 확인받습니다.
6. 모호한 연결은 후보를 사용자에게 보여줍니다. AI가 언급되지 않은 사실을 확정하지 않습니다.
7. 백엔드가 검증한 허용 필드만 변경합니다. AI의 `changes`를 엔티티에 그대로 복사하지 않습니다.
8. 잠금 단위는 관리 항목 한 개입니다. 잠금 보유는 승인 권한이 아니며 최종 반영 시 권한·버전·잠금을 다시 검사합니다. TTL·갱신 주기 등은 미정입니다.
9. 일반 항목 삭제는 삭제 표시·이력을 보존합니다. 원본 삭제는 원문과 그 내용을 복사한 제안·근거·현재 값·이력 등의 파생 내용을 제거합니다. 연결 해제만으로 끝내거나 소유자 승인 대기로 미루지 않습니다.
10. 독립된 유효 근거가 사라진 항목은 소유자 재확인 전 현황판·새 공유 대상에서 제외합니다. 늦은 AI 결과·이전 편집·반복 요청으로 삭제 내용이 다시 노출되지 않도록 검사합니다.

## 도메인 패키지 구조

루트는 `com.hanmaum.backend`입니다. 합의한 도메인별 최상위 패키지를 미리 준비하고, 미구현 도메인은 `package-info.java`에 책임을 기록합니다. `auth`와 아래 8개 업무 도메인은 `code`, `controller`, `service`, `repository`, `entity`, `dto`의 공통 하위 폴더까지 준비하며 빈 폴더는 `.gitkeep`으로 Git에 보존합니다. `ai`는 통신 어댑터 구조, `global`은 공통 코드·응답·예외·문서·보안·설정 구조를 사용합니다.

담당자는 실제 파일 추가 시 해당 폴더의 `.gitkeep`을 제거하고 불필요한 계층은 삭제하거나 조정할 수 있습니다. 공통 폴더 구조가 모든 도메인에 독립 엔티티·테이블을 만들라는 의미는 아닙니다. 업무 클래스와 영속성 모델은 기능 구현 시 추가합니다.

| 패키지 | 책임 | 현재 상태 |
| --- | --- | --- |
| `auth` | 로그인·로그아웃·CSRF의 HTTP 계약 | CSRF Controller 존재, 로그인·로그아웃은 Security 필터 처리 |
| `user` | 서비스 회원·소셜 계정 매핑·탈퇴 | 저장 구조, OAuth 회원 생성/조회, 회원 연결 유효성 검증·내 정보 조회 구현. 계정 연결·탈퇴는 후속 구현 |
| `carespace` | 공간·참여·초대·소유권 | 생성·참여 목록·상세 조회, 현재 참여자·소유자 검증 구현. 초대·수정·삭제·이전 API는 후속 |
| `record` | 원본 소식 작성·조회·삭제 | 패키지 준비, 기능 미구현 |
| `analysis` | 분석 실행·상태·재시도 관리 | 패키지 준비, 기능 미구현 |
| `proposal` | AI 제안·구성원 변경 요청·최종 반영 | 패키지 준비, 기능 미구현 |
| `careitem` | 다섯 항목 유형·잠금·근거·이력 | 패키지 준비, 기능 미구현 |
| `dashboard` | 현재 유효한 항목의 현황 조회 | 패키지 준비, 기능 미구현 |
| `sharing` | 공유 링크·현재 접근 권한 확인 | 패키지 준비, 기능 미구현 |
| `ai` | 내부 FastAPI 클라이언트·설정·DTO | 기존 통신 어댑터 유지 |
| `global` | 공통 설정·보안·응답·예외 | 기존 기반 확장 |

`Common`은 API 명세의 공통 분류입니다. `global.command`는 동기 요청의 트랜잭션 잠금·요청 비교·성공 결과 저장을 담당하며 현재 공간 생성에서 사용합니다. 별도 반복 요청 결과 조회 API는 구현하지 않습니다.

- Controller는 Service를 호출하고 엔티티 대신 공개 DTO를 반환합니다. 공개 API는 `/api` 기준이며 `/api/v1`로 임의 변경하지 않습니다.
- Service는 업무 규칙·트랜잭션, Repository는 해당 도메인의 영속성 접근을 담당합니다.
- 도메인 간 업무 접근은 Service 경계를 사용합니다. 다른 도메인의 Controller 호출이나 무분별한 Repository 공유를 피합니다.
- 공개 `analysis` 업무는 `ai` 어댑터를 호출합니다. 내부 DTO의 수치 제한·버전 타입을 공개 API 정책으로 그대로 사용하지 않습니다.
- `global.response`는 업무 도메인에 의존하지 않습니다. 전역 예외 처리에서 내부 AI 실패를 공개 오류로 변환하는 기존 경계는 유지합니다.
- `global.code.ErrorCode`는 공통 오류와 도메인 오류가 구현하는 인터페이스입니다. `CommonErrorCode`는 도메인 공통 오류, `SuccessCode`는 성공 응답의 코드·메시지를 담당합니다. 공개 코드·HTTP 상태·기본 메시지는 패키지 위치와 독립된 API 계약입니다.
- 도메인별 오류는 각 `code` 패키지에 둡니다. 현재 OAuth 실패는 `auth`, 항목 잠금은 `careitem`, 제안 묶음 충돌은 `proposal`에서 관리합니다. 버전·반복 요청·삭제 영향 등 여러 도메인에 적용되는 오류는 공통 코드로 재사용합니다.
- `global.exception`은 `ApiException`과 전역 예외 변환, `global.openapi`는 오류 enum 탐색·코드 중복 검사·Swagger 응답 등록, `global.config`는 OpenAPI 기본 설정 등을 담당합니다. 미구현 도메인의 오류 enum이나 API를 임의로 만들지 않습니다.
- 공개 응답은 [API 공통 규격](api-conventions.md), 내부 계약은 [AI 계약](ai-contract.md)을 따릅니다.

ERD와 노션 API는 검토 가능한 초안이며 전체 물리 스키마·업무 구현 완료를 뜻하지 않습니다. Flyway V1은 세션 테이블, V2는 `app_user`·`social_account` 저장 구조를 담당합니다. V2는 `(provider, provider_user_id)` 유일성과 사용자 FK를 검사하며 사용자 행 삭제 시 해당 소셜 연결만 제거합니다. 회원 탈퇴 전 공간 소유권 검사·공동 기록 보존·세션 종료는 후속 업무 구현 범위입니다. 입력 제한·페이지네이션·잠금 TTL·검토/삭제 확인값 구현은 해당 기능 전에 합의합니다.

### 돌봄 공간 생성·조회

2026-10-10 사용자 합의 기준입니다. 공개 입출력과 오류는 [API 공통 규격의 공간 계약](api-conventions.md#돌봄-공간-api)을 따릅니다.

- Flyway V3는 `care_space`, `space_membership`, `command_receipt`를 추가합니다. 기존 V1·V2는 변경하지 않습니다. 기존 ERD 초안의 nullable 호칭은 필수로 변경했고, 실제 ERD Cloud와 노션을 자동 갱신한 것은 아닙니다.
- `care_space`의 소유자는 `owner_membership_id`입니다. 현재 소유자별 호칭 유일성을 위해 `owner_user_id`를 함께 저장하고 `(owner_user_id, subject_label)`을 UNIQUE로 검사합니다. 복합 FK로 공간·참여·사용자와 활성 여부가 함께 일치하도록 하므로 두 소유자 정보가 어긋날 수 없습니다.
- `owner_active=true`와 참여의 생성 컬럼 `is_active`는 DB 내부 제약용입니다. 소유자는 같은 공간의 현재 참여자 한 명이어야 하며, FK는 트랜잭션 종료까지 지연하여 공간과 최초 참여를 함께 생성할 수 있게 합니다. 참여 종료·사용자 연결 해제도 현재 소유자라면 FK로 차단됩니다. 소유권 이전 시 사용자 ID와 참여 ID를 함께 변경해야 합니다.
- 같은 공간·사용자의 활성 참여는 부분 UNIQUE 인덱스로 하나만 허용합니다. 종료 이력은 유지할 수 있습니다. 초대 저장 구조와 `invitation_id` FK는 초대 기능에서 추가하며, 이번에 미구현 테이블을 만들지 않습니다.
- 이번 도메인은 원자적인 `INSERT ... ON CONFLICT`, 지연 FK, 행 잠금과 집계 조회를 명시하기 위해 `JdbcTemplate` Repository와 불변 저장 모델(record)을 사용합니다. 기존 회원 JPA 구현과 같은 Spring 트랜잭션·DataSource를 공유합니다. `carespace.entity`의 record는 JPA 엔티티가 아니며 Hibernate 스키마 검증 대상도 아니므로 PostgreSQL 통합 테스트에서 제약을 검증합니다. 테이블 변경은 Flyway가 담당합니다.
- `CareSpaceCreationService`는 `READ_COMMITTED` 트랜잭션에서 요청 잠금 → 기존 결과 확인 → 공간·최초 참여 생성 → 성공 기록 순으로 처리합니다. 모두 커밋하거나 모두 롤백하며 FK 최종 검사에 실패해도 응답 전에 롤백됩니다. 동일 호칭의 동시 생성은 DB UNIQUE 인덱스가 판정합니다.
- 초기 공간 버전은 1, 상태는 ACTIVE이며 생성·수정 시각은 같습니다. 조회·재요청·실패는 버전과 수정 시각을 변경하지 않습니다. 공간 정보·소유권·현재 참여 변경 시 버전/수정 시각을 업무 트랜잭션당 한 번 갱신하는 것은 후속 변경 API의 책임입니다.
- 목록·상세 조회는 현재 참여·역할·인원수를 하나의 SQL 스냅샷에서 계산합니다. 종료된 참여와 DELETING 공간을 제외하며 목록은 요청자의 참여 시각, 공간 UUID 오름차순입니다. 별도 role 컬럼이나 생성자 기반 중복 제한을 두지 않습니다.

#### 다른 도메인의 권한 확인

`CareSpaceAccessService.requireActiveMember(userId, spaceId)`와 `requireOwner(userId, spaceId)`는 내부 Service 계약입니다. 검증 결과 `CareSpaceAccess`에는 공간 ID, 현재 참여 ID, 역할, 숫자 버전만 포함합니다. 외부 권한 조회 API나 세션에 저장하는 권한 캐시가 아닙니다.

- 호출자는 **READ_COMMITTED 쓰기 트랜잭션 안에서** 권한 검사와 실제 업무 변경을 함께 수행합니다. 트랜잭션이 없거나 읽기 전용이면 잘못된 사용으로 실패합니다.
- 공간 → 현재 참여 순서로 `FOR UPDATE` 잠금을 획득해 커밋/롤백까지 유지합니다. 후속 참여 종료·소유권 이전·삭제 등도 같은 잠금 순서를 사용해야 합니다. 여러 공간을 변경하는 기능은 공간 ID 순서로 잠금 순서를 맞춰야 합니다.
- 없음/DELETING은 `RESOURCE_NOT_FOUND`, 비참여/종료 참여/소유자 아님은 `FORBIDDEN`입니다. 반환한 결과를 트랜잭션 밖에서 재사용하지 않습니다. 외부 AI 통신 중 잠금을 유지하지 않습니다.
- 이번 읽기 API는 한 SQL의 참여 조건으로 데이터 노출을 검사합니다. 다른 도메인의 조회도 같은 스냅샷에서 권한과 대상 데이터를 확인하거나 적절한 트랜잭션 잠금을 사용해야 합니다. 조회 이전의 독립 권한 검사만으로 이후 변경 권한을 보장하지 않습니다.

#### 반복 요청 저장과 운영 설정

- 요청 잠금의 범위는 `(actor_user_id, client_request_id)`이며 모든 command에서 같은 규칙을 사용해야 합니다. PostgreSQL `pg_try_advisory_xact_lock`이 실패하면 `409 REQUEST_IN_PROGRESS`입니다. 해시 충돌은 일시적인 재시도만 유발하며 결과 조회는 전체 UUID 키로 합니다.
- 처리 중 상태를 별도 커밋하지 않습니다. 현재 성공 영수증만 저장하므로 프로세스 종료/실패 시 DB 트랜잭션이 롤백되고 잠금이 해제됩니다. 멈춘 IN_PROGRESS 행이나 임의의 잠금 TTL을 만들지 않습니다. 처리 중에는 아직 커밋된 내용이 없어 409 처리 중을 반환하고, 성공 후 재요청에서 원래 내용과의 일치를 검사합니다.
- HMAC-SHA256 입력에는 사용자·요청 ID·업무 종류·범위·정규화된 본문을 길이 구분하여 포함합니다. DB에는 digest와 최소 결과 ID만 저장하고 원문/전체 응답은 저장하지 않습니다. `COMMAND_DIGEST_KEY`는 DB 외부의 안정된 비밀값이며 최소 32 UTF-8 바이트입니다.
- local/test의 기본 키는 개발 전용입니다. 운영은 비밀 관리 환경에서 충분한 엔트로피의 키를 주입하며 모든 인스턴스·재시작에서 유지합니다. 단순 교체하면 이전 영수증과 비교할 수 없으므로 키 교체 전 별도 버전/이관 계획이 필요합니다.
- 성공 재요청은 현재 참여와 원래 참여 ID를 다시 확인합니다. 소유권만 이전하고 참여를 유지한 경우 기존 생성 결과를 반환하지만 나갔다가 새 참여로 재가입한 경우 과거 참여 ID를 반환하지 않습니다. 공간이 삭제됐어도 영수증만 보고 공간을 재생성하지 않습니다.
- 영수증 자동 만료·삭제는 구현하지 않습니다. 보관 기간과 탈퇴/삭제 정리, DELETING 공간 호칭 재사용 정책은 후속 합의 대상입니다. 현재 UNIQUE 제약은 남아 있는 공간 행의 호칭을 예약하며 삭제 API가 없어 이를 해제하는 기능도 없습니다.

FE는 입력 정규화·문자 수 계산, 요청 ID 재사용과 세 오류 코드의 분기를 맞춰야 합니다. AI 호출 의존성은 없습니다. 이번 범위는 공간 생성·조회 기반이며 전체 참여 상태 전이·삭제 전파 구현 완료를 의미하지 않습니다.

### OAuth 회원 매핑

- `global.security.oauth`는 Spring Security의 기본 Google OIDC·Kakao OAuth2 사용자 조회/검증을 위임하고, 검증된 제공자 식별자를 `user.service.SocialLoginMemberService`로 전달합니다. 제공자 HTTP 통신 동안 회원 DB 트랜잭션을 열어두지 않습니다.
- 식별 기준은 Google ID Token의 `sub`, Kakao의 정수 `id`와 제공자 구분입니다. 이메일·표시 이름으로 계정을 연결하지 않습니다.
- 회원 조회/생성은 `READ_COMMITTED` 트랜잭션에서 제공자 식별자별 `pg_advisory_xact_lock`을 획득한 뒤 수행합니다. 잠금은 같은 DB를 사용하는 여러 서버에서도 적용되고 커밋/롤백 때 해제됩니다. 해시 충돌은 처리 순서에만 영향을 주며 실제 조회·유일성 검사는 전체 `(provider, provider_user_id)`로 수행합니다. 관련 생성 경로는 이 서비스를 사용해야 합니다.
- 최초 가입에서만 제공자 이름을 저장하고 이름이 없으면 null을 허용합니다. 재로그인은 기존 이름과 `updated_at`을 유지합니다(2026-10-09 사용자 합의). 별도 이름 수정 정책은 미정입니다.
- 회원과 소셜 연결 생성은 전체 성공 또는 전체 롤백입니다. DB 실패는 기존 로그인 실패 응답으로 변환하며 SQL 파라미터·제공자 원문을 응답에 포함하지 않습니다.
- 로그인 성공 시 `MemberPrincipal`에 서비스 사용자 UUID를 연결하고 인증 이름도 UUID로 사용합니다. Google은 `OidcUser` 형식과 검증 결과를 유지하며 두 제공자 모두 JDBC 세션 저장·복원 후 같은 회원을 식별합니다. 기존 제공자 전용 세션은 자동 변환하지 않고 재로그인을 요구합니다.
- 로그인한 회원이 필요한 업무 Controller는 `@CurrentUser AuthenticatedUser`를 사용합니다. `global.security.CurrentUserArgumentResolver`가 인증된 `MemberPrincipal`을 확인하고, `user.service.MemberIdentityService`가 UUID·제공자·제공자 사용자 ID에 대응하는 현재 DB 연결을 검증합니다. 사용자 FK로 회원 존재를 보장하며 없는 회원·끊어진 연결·UUID 불일치는 `401 UNAUTHENTICATED`입니다. DB 장애는 `500 INTERNAL_ERROR`이며 두 경우 모두 Controller의 업무 메서드를 호출하지 않습니다.
- `global.config.WebMvcConfig`가 공통 처리기를 MVC에 등록합니다. 요청에서 사용자 ID를 바인딩하지 않고 검증된 UUID만 Controller에 전달하며 엔티티·제공자 정보는 노출하지 않습니다. 검증은 요청마다 수행하되 공개 API에는 일괄 적용하지 않습니다. Security 필터의 경로 접근·CSRF 검사와 각 도메인 Service의 공간 참여·권한 검사는 별도로 유지합니다.
- `GET /api/users/me`는 공통 회원 검증 후 `UserProfileService`에서 현재 DB의 이름·연결된 제공자만 공개 DTO로 반환합니다. 사용자 ID를 입력받거나 전역 공간 역할을 반환하지 않습니다. 조회는 회원·연결을 생성하지 않으며, 조회 시점에 회원이 사라졌다면 `401 UNAUTHENTICATED`입니다. URL·응답 필드·세션 쿠키 계약은 그대로 유지합니다.
- 실제 제공자 로그인 검증과 가짜 제공자 기반 자동 검증을 구분합니다. 회원 탈퇴 시 모든 세션 종료와 소유권 검사는 후속 구현 범위입니다.

구현 참고: [Spring Security 사용자 서비스 확장](https://docs.spring.io/spring-security/reference/servlet/oauth2/login/advanced.html), [PostgreSQL 트랜잭션 advisory lock](https://www.postgresql.org/docs/17/explicit-locking.html#ADVISORY-LOCKS), [Google 식별자](https://developers.google.com/identity/openid-connect/openid-connect), [Kakao 사용자 정보](https://developers.kakao.com/docs/ko/kakaologin/rest-api#req-user-info).

## 운영 기준

- 개발: 로컬 Java·Python 프로세스와 Docker PostgreSQL
- 초기 배포: 외부 LLM API를 사용하는 소규모 MVP, Lightsail Linux 2 vCPU·4GB급에서 시작
- Nginx를 통해 동일 도메인·HTTPS 제공, Spring·AI·DB 내부 통신
- 운영 DB 비밀값은 환경변수로 주입하고 DB 백업은 별도 저장소에 보관
- 단일 서버 장애 시 전체 서비스가 중단될 수 있으므로 실제 이용 규모에 맞춰 DB·애플리케이션 분리 검토
- 합성 기록으로 먼저 검증하고, 실제 부모님 정보를 사용하기 전 동의·열람 범위·공유 내용·데이터 보관 정책 구체화

Redis, 벡터 DB, Spring AI, 메시지 브로커는 초기 의존성에 포함하지 않습니다. 실제 요구와 측정 결과에 따라 도입합니다.
