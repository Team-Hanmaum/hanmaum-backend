# 한마음 백엔드 설계 기준

## 서비스 범위

기획서의 Must Have를 MVP 기준으로 삼습니다. 원본 소식에서 일정·할 일·확인사항·관찰·안내를 제안하고, 사용자가 확정한 내용으로 현재 상태를 갱신합니다.

## 역할 분담

- Spring: 인증, 공간 접근 권한, 원본 저장, 해당 공간의 기존 후보 조회, 제안 저장, 사용자 확정, 트랜잭션, 현재 상태와 변경 이력, 현황판·공유 데이터
- FastAPI: 자연어 항목 추출, 기존 후보와의 관계 판단, 추가·변경·해소 제안 및 근거 반환
- FastAPI는 서비스 DB에 직접 변경을 적용하지 않습니다. Spring은 LLM 호출 중 DB 트랜잭션을 유지하지 않습니다.

## 공간 권한

권한은 계정 전체가 아닌 돌봄 공간 구성원 관계에 저장합니다.

| 작업 | OWNER | MEMBER |
| --- | --- | --- |
| 현재 참여 공간의 소식·항목·근거·이력 조회 | 가능 | 가능 |
| 소식 작성·AI 제안 검토·가족 초대 | 가능 | 가능 |
| AI 제안 반영·항목 등록·수정·담당자 변경·일반 삭제 | 최종 반영 | 변경 요청 |
| 할 일 진행 상태 변경 | 모든 할 일 | 본인 담당은 직접, 나머지는 요청 |
| 질문 답변 제출 | 가능 | 가능 |
| 답변 확인·질문 해소·공간 정보 수정 | 최종 반영 | 변경 요청 |
| 소식 원본 삭제 | 공간 내 모든 원본 | 본인 원본 |
| 구성원 내보내기 | 가능 | 불가 |
| 돌봄 공간 전체 삭제 | 가능 | 불가 |

모든 조회·변경·공유·AI 후보 조회에서 현재 참여 상태와 대상별 권한을 확인합니다. 초대 링크는 발급 후 24시간 유효하며 별도 가입 승인은 없습니다. 이미 참여한 사용자는 중복 참여시키지 않습니다.

소유권은 현재 구성원 한 명에게 원자적으로 이전하고 기존 소유자는 구성원이 됩니다. 공간마다 소유자 한 명을 유지합니다. 소유자는 소유권 이전 또는 공간 삭제 후 나가기·탈퇴가 가능합니다. 참여 종료 시 미완료 담당 할 일은 미지정으로 전환하고 완료 상태·공동 기록·이력은 유지해야 합니다. 현재 소유권 이전·참여 종료·접근 차단을 구현했으며, 담당 해제와 공간 삭제·회원 탈퇴는 후속 구현입니다.

## 데이터 변경 원칙

1. 원본 소식과 AI 제안, 확정된 관리 항목을 구분합니다.
2. AI 제안의 대상 ID·근거·생성 시점 버전을 보존합니다.
3. 확정할 때 현재 구성원 권한과 현재 항목 버전을 다시 검사합니다.
4. 선택한 제안 전체를 검증하고 현재 항목 변경·이력 기록·제안 적용·성공 처리 기록을 함께 확정합니다. 한 항목이라도 충돌하면 전체 미반영하며 선택하지 않은 제안은 검토 대기로 유지합니다.
5. 같은 제안의 재확정은 중복 적용하지 않습니다. 다른 가족이 항목을 변경했다면 다시 확인받습니다.
6. 모호한 연결은 후보를 사용자에게 보여줍니다. AI가 언급되지 않은 사실을 확정하지 않습니다.
7. 백엔드가 검증한 허용 필드만 변경합니다. AI의 `changes`를 엔티티에 그대로 복사하지 않습니다.
8. 잠금 단위는 관리 항목 한 개입니다. 잠금 보유는 승인 권한이 아니며 최종 반영 시 권한·버전·잠금을 다시 검사합니다. TTL·갱신 주기 등은 미정입니다.
9. 일반 항목 삭제는 삭제 표시·이력을 보존합니다. 원본 삭제는 원문과 그 내용을 복사한 제안·근거·현재 값·이력 등의 파생 내용을 제거합니다. 연결 해제만으로 끝내거나 소유자 승인 대기로 미루지 않습니다.
10. 독립된 유효 근거가 사라진 항목은 소유자 재확인 전 현황판·새 공유 대상에서 제외합니다. 늦은 AI 결과·이전 편집·반복 요청으로 삭제 내용이 다시 노출되지 않도록 검사합니다.

## 도메인 패키지 구조

루트는 `com.hanmaum.backend`입니다. 합의한 도메인별 최상위 패키지를 미리 준비하고, 미구현 도메인은 `package-info.java`에 책임을 기록합니다. `auth`와 아래 8개 업무 도메인은 `code`, `controller`, `service`, `repository`, `entity`, `dto`의 공통 하위 폴더까지 준비하며 빈 폴더는 `.gitkeep`으로 Git에 보존합니다. `ai`는 통신 어댑터 구조, `global`은 공통 코드·응답·예외·문서·보안·설정 구조를 사용합니다.

담당자는 실제 파일 추가 시 해당 폴더의 `.gitkeep`을 제거하고 불필요한 계층은 삭제하거나 조정할 수 있습니다. 공통 폴더 구조가 모든 도메인에 독립 엔티티·테이블을 만들라는 의미는 아닙니다. 업무 클래스와 영속성 모델은 기능 구현 시 추가합니다.

| 패키지 | 책임 | 현재 상태 |
| --- | --- | --- |
| `auth` | 로그인·로그아웃·CSRF의 HTTP 계약 | CSRF Controller 존재, 로그인·로그아웃은 Security 필터 처리 |
| `user` | 서비스 회원·소셜 계정 매핑·탈퇴 | 저장 구조, OAuth 회원 생성/조회, 회원 연결 유효성 검증·내 정보 조회 구현. 계정 연결·탈퇴는 후속 구현 |
| `carespace` | 공간·참여·초대·소유권 | 생성·조회·초대·참여·구성원 목록·소유권 이전·나가기/내보내기 구현. 공간 수정/삭제 및 CareItem 담당·잠금 연동은 후속 |
| `record` | 원본 소식 작성·조회·삭제 | 원본 저장·커서 목록·상세 조회와 최초 분석 접수 구현. 삭제 API는 후속 |
| `analysis` | 분석 실행·상태·재시도 관리 | DB 대기열·실행·상태·실패 재시도·중단 복구·삭제 전파 연결점 구현. 운영 실행값은 미정 |
| `proposal` | AI 제안·구성원 변경 요청·최종 반영 | CREATE 제안·문서·근거 저장 및 목록·상세 조회 구현. 수정·변경 요청·최종 반영은 후속 |
| `careitem` | 다섯 항목 유형·잠금·근거·이력 | 일정 직접 등록·목록·상세, 직접 입력 근거·최초 이력·분석 후보 구현. 다른 유형 등록·승인·수정·잠금은 후속 |
| `dashboard` | 현재 유효한 항목의 현황 조회 | 패키지 준비, 기능 미구현 |
| `sharing` | 공유 링크·현재 접근 권한 확인 | 패키지 준비, 기능 미구현 |
| `ai` | 내부 FastAPI 클라이언트·설정·DTO | 기존 통신 어댑터 유지 |
| `global` | 공통 설정·보안·응답·예외 | 기존 기반 확장 |

`Common`은 API 명세의 공통 분류입니다. `global.command`는 동기 요청의 트랜잭션 잠금·요청 비교·성공 결과 저장을 담당하며 공간 생성·초대 발급·참여·소유권 이전·참여 종료에서 사용합니다. 별도 반복 요청 결과 조회 API는 구현하지 않습니다.

- Controller는 Service를 호출하고 엔티티 대신 공개 DTO를 반환합니다. 공개 API는 `/api` 기준이며 `/api/v1`로 임의 변경하지 않습니다.
- Service는 업무 규칙·트랜잭션, Repository는 해당 도메인의 영속성 접근을 담당합니다.
- 도메인 간 업무 접근은 Service 경계를 사용합니다. 다른 도메인의 Controller 호출이나 무분별한 Repository 공유를 피합니다.
- 공개 `analysis` 업무는 `ai` 어댑터를 호출합니다. 내부 DTO의 수치 제한·버전 타입을 공개 API 정책으로 그대로 사용하지 않습니다.
- `global.response`는 업무 도메인에 의존하지 않습니다. 전역 예외 처리에서 내부 AI 실패를 공개 오류로 변환하는 기존 경계는 유지합니다.
- `global.code.ErrorCode`는 공통 오류와 도메인 오류가 구현하는 인터페이스입니다. `CommonErrorCode`는 도메인 공통 오류, `SuccessCode`는 성공 응답의 코드·메시지를 담당합니다. 공개 코드·HTTP 상태·기본 메시지는 패키지 위치와 독립된 API 계약입니다.
- 도메인별 오류는 각 `code` 패키지에 둡니다. 현재 OAuth 실패는 `auth`, 항목 잠금은 `careitem`, 제안 묶음 충돌은 `proposal`에서 관리합니다. 버전·반복 요청·삭제 영향 등 여러 도메인에 적용되는 오류는 공통 코드로 재사용합니다.
- `global.exception`은 `ApiException`과 전역 예외 변환, `global.openapi`는 오류 enum 탐색·코드 중복 검사·Swagger 응답 등록, `global.config`는 OpenAPI 기본 설정 등을 담당합니다. 미구현 도메인의 오류 enum이나 API를 임의로 만들지 않습니다.
- 공개 응답은 [API 공통 규격](api-conventions.md), 내부 계약은 [AI 계약](ai-contract.md)을 따릅니다.

ERD와 노션 API는 검토 가능한 초안이며 전체 물리 스키마·업무 구현 완료를 뜻하지 않습니다. Flyway V1은 세션 테이블, V2는 `app_user`·`social_account` 저장 구조를 담당합니다. V2는 `(provider, provider_user_id)` 유일성과 사용자 FK를 검사하며 사용자 행 삭제 시 해당 소셜 연결만 제거합니다. 회원 탈퇴 전 공간 소유권 검사·공동 기록 보존·세션 종료는 후속 업무 구현 범위입니다. 입력 제한·페이지네이션·잠금 TTL·검토/삭제 확인값 구현은 해당 기능 전에 합의합니다.

### 돌봄 공간 생성·조회

2026-10-10 사용자 합의 기준입니다. 공개 입출력과 오류는 [API 공통 규격의 공간 계약](api-conventions.md#돌봄-공간-api)을 따릅니다.

- Flyway V3는 `care_space`, `space_membership`, `command_receipt`를 추가합니다. 기존 V1·V2는 변경하지 않습니다. 기존 ERD 초안의 nullable 호칭은 필수로 변경했고, 실제 ERD Cloud와 노션을 자동 갱신한 것은 아닙니다.
- `care_space`의 소유자는 `owner_membership_id`입니다. 현재 소유자별 호칭 유일성을 위해 `owner_user_id`를 함께 저장하고 `(owner_user_id, subject_label)`을 UNIQUE로 검사합니다. 복합 FK로 공간·참여·사용자와 활성 여부가 함께 일치하도록 하므로 두 소유자 정보가 어긋날 수 없습니다.
- `owner_active=true`와 참여의 생성 컬럼 `is_active`는 DB 내부 제약용입니다. 소유자는 같은 공간의 현재 참여자 한 명이어야 하며, FK는 트랜잭션 종료까지 지연하여 공간과 최초 참여를 함께 생성할 수 있게 합니다. 참여 종료·사용자 연결 해제도 현재 소유자라면 FK로 차단됩니다. 소유권 이전 시 사용자 ID와 참여 ID를 함께 변경해야 합니다.
- 같은 공간·사용자의 활성 참여는 부분 UNIQUE 인덱스로 하나만 허용합니다. 종료 이력은 유지할 수 있습니다. V4에서 초대 저장 구조와 `invitation_id` FK를 추가합니다.
- 이번 도메인은 원자적인 `INSERT ... ON CONFLICT`, 지연 FK, 행 잠금과 집계 조회를 명시하기 위해 `JdbcTemplate` Repository와 불변 저장 모델(record)을 사용합니다. 기존 회원 JPA 구현과 같은 Spring 트랜잭션·DataSource를 공유합니다. `carespace.entity`의 record는 JPA 엔티티가 아니며 Hibernate 스키마 검증 대상도 아니므로 PostgreSQL 통합 테스트에서 제약을 검증합니다. 테이블 변경은 Flyway가 담당합니다.
- `CareSpaceCreationService`는 `READ_COMMITTED` 트랜잭션에서 요청 잠금 → 기존 결과 확인 → 공간·최초 참여 생성 → 성공 기록 순으로 처리합니다. 모두 커밋하거나 모두 롤백하며 FK 최종 검사에 실패해도 응답 전에 롤백됩니다. 동일 호칭의 동시 생성은 DB UNIQUE 인덱스가 판정합니다.
- 초기 공간 버전은 1, 상태는 ACTIVE이며 생성·수정 시각은 같습니다. 조회·재요청·실패는 버전과 수정 시각을 변경하지 않습니다. 신규 참여·소유권 이전·참여 종료는 버전/수정 시각을 한 번 갱신합니다. 후속 공간 정보 변경도 업무 트랜잭션당 한 번 갱신해야 합니다.
- 목록·상세 조회는 현재 참여·역할·인원수를 하나의 SQL 스냅샷에서 계산합니다. 종료된 참여와 DELETING 공간을 제외하며 목록은 요청자의 참여 시각, 공간 UUID 오름차순입니다. 별도 role 컬럼이나 생성자 기반 중복 제한을 두지 않습니다.

#### 다른 도메인의 권한 확인

`CareSpaceAccessService.requireActiveMember(userId, spaceId)`와 `requireOwner(userId, spaceId)`는 내부 Service 계약입니다. 검증 결과 `CareSpaceAccess`에는 공간 ID, 현재 참여 ID, 역할, 숫자 버전만 포함합니다. 외부 권한 조회 API나 세션에 저장하는 권한 캐시가 아닙니다.

- 호출자는 **READ_COMMITTED 쓰기 트랜잭션 안에서** 권한 검사와 실제 업무 변경을 함께 수행합니다. 트랜잭션이 없거나 읽기 전용이면 잘못된 사용으로 실패합니다.
- 공간 → 현재 참여 순서로 `FOR UPDATE` 잠금을 획득해 커밋/롤백까지 유지합니다. 후속 참여 종료·소유권 이전·삭제 등도 같은 잠금 순서를 사용해야 합니다. 여러 공간을 변경하는 기능은 공간 ID 순서로 잠금 순서를 맞춰야 합니다.
- 없음/DELETING은 `RESOURCE_NOT_FOUND`, 비참여/종료 참여/소유자 아님은 `FORBIDDEN`입니다. 반환한 결과를 트랜잭션 밖에서 재사용하지 않습니다. 외부 AI 통신 중 잠금을 유지하지 않습니다.
- 공간 목록·상세·구성원 목록은 한 SQL의 참여 조건으로 데이터 노출을 검사합니다. 초대 확인은 공간·발급 참여·현재 참여를 잠근 상태에서 검사하며 실제 데이터 변경은 하지 않습니다. 다른 도메인의 조회도 같은 스냅샷에서 권한과 대상 데이터를 확인하거나 적절한 트랜잭션 잠금을 사용해야 합니다. 조회 이전의 독립 권한 검사만으로 이후 변경 권한을 보장하지 않습니다.

#### 반복 요청 저장과 운영 설정

- 요청 잠금의 범위는 `(actor_user_id, client_request_id)`이며 모든 command에서 같은 규칙을 사용해야 합니다. PostgreSQL `pg_try_advisory_xact_lock`이 실패하면 `409 REQUEST_IN_PROGRESS`입니다. 해시 충돌은 일시적인 재시도만 유발하며 결과 조회는 전체 UUID 키로 합니다.
- 처리 중 상태를 별도 커밋하지 않습니다. 현재 성공 영수증만 저장하므로 프로세스 종료/실패 시 DB 트랜잭션이 롤백되고 잠금이 해제됩니다. 멈춘 IN_PROGRESS 행이나 임의의 잠금 TTL을 만들지 않습니다. 처리 중에는 아직 커밋된 내용이 없어 409 처리 중을 반환하고, 성공 후 재요청에서 원래 내용과의 일치를 검사합니다.
- HMAC-SHA256 입력에는 사용자·요청 ID·업무 종류·범위·정규화된 본문을 길이 구분하여 포함합니다. DB에는 digest와 최소 결과 ID·버전·시각 등 처리 메타데이터만 저장하고 원문/전체 응답은 저장하지 않습니다. `COMMAND_DIGEST_KEY`는 DB 외부의 안정된 비밀값이며 최소 32 UTF-8 바이트입니다.
- local/test의 기본 키는 개발 전용입니다. 운영은 비밀 관리 환경에서 충분한 엔트로피의 키를 주입하며 모든 인스턴스·재시작에서 유지합니다. 단순 교체하면 이전 영수증과 비교할 수 없으므로 키 교체 전 별도 버전/이관 계획이 필요합니다.
- 성공 재요청은 원칙적으로 현재 참여와 원래 참여 ID를 다시 확인합니다. 소유권만 이전하고 참여를 유지한 경우 기존 생성 결과를 반환하지만 나갔다가 새 참여로 재가입한 경우 과거 생성/가입 결과를 반환하지 않습니다. **본인 나가기 성공 기록만 예외**로 원래 종료 참여 ID·시각을 반환하며 현재 공간 데이터나 권한은 제공하지 않습니다. 공간이 삭제됐어도 영수증만 보고 공간을 재생성하지 않습니다.
- 영수증 자동 만료·삭제는 구현하지 않습니다. 보관 기간과 탈퇴/삭제 정리, DELETING 공간 호칭 재사용 정책은 후속 합의 대상입니다. 현재 UNIQUE 제약은 남아 있는 공간 행의 호칭을 예약하며 삭제 API가 없어 이를 해제하는 기능도 없습니다.

FE는 입력 정규화·문자 수 계산과 각 API의 요청 ID·오류 분기를 맞춰야 합니다. AI 호출 의존성은 없습니다. 참여 종료의 CareItem 연동과 공간/원본 삭제 전파는 후속 구현입니다.

### 가족 초대·공간 참여·구성원 조회

2026-10-11 합의 기준이며 공개 필드·오류·FE 의존성은 [초대 API 계약](api-conventions.md#가족-초대참여구성원-api)을 따릅니다.

- V4는 `invitation`과 nullable `space_membership.invitation_id`를 추가합니다. `(space_id, issued_by_membership_id)`와 `(space_id, invitation_id)`의 복합 FK로 다른 공간의 발급자/초대 연결을 차단합니다. V1~V3와 기존 회원·세션·공간·참여·영수증은 유지하며 기존 참여의 초대 ID는 null입니다.
- 초대는 발급 **당시 참여 ID**에 묶입니다. 같은 사용자가 다시 참여해도 그 이전 참여로 발급한 링크는 무효입니다. 별도 중복 revoked 상태를 두지 않고 조회/참여 시 발급 참여와 ACTIVE 공간을 검증합니다. 후속 나가기·내보내기에서도 이 모델을 유지해야 합니다.
- `InvitationService`는 READ_COMMITTED에서 요청 잠금 → 공간 → 발급 참여 → 현재 참여 순서로 검사합니다. 현재 참여가 없는 경우에도 공간 잠금으로 같은 공간의 참여 변경을 직렬화하고, 부분 UNIQUE를 최종 방어로 유지합니다. 대기 후 현재 참여/발급 참여/만료를 다시 확인하여 중복 참여·버전 갱신 유실을 막습니다. 후속 종료·이전·삭제도 반드시 공간부터 잠가야 합니다.
- 새 참여·공간 버전/수정 시각·성공 영수증은 원자적으로 저장합니다. 기존 참여 확인은 같은 참여를 반환하며 소유자를 바꾸지 않습니다. 종료 이력 뒤의 재참여는 마지막 종료 시각보다 나중에 발급된 초대로 새 참여를 만듭니다. UTC Clock을 주입하고 PostgreSQL 저장 정밀도에 맞춰 마이크로초로 기록합니다.
- 발급 요청 종류는 `ISSUE_INVITATION`, 범위는 `SPACE:<UUID>`입니다. 참여는 `JOIN_INVITATION`, 범위는 `INVITATION_HASH:<SHA-256>`입니다. 공유 요청 잠금과 HMAC을 재사용하여 같은 사용자·요청 ID의 업무/대상 변경을 거부합니다. 영수증에는 최소 결과 ID와 참여 신규 여부만 저장하며 원문 토큰·URL·전체 응답은 넣지 않습니다.
- 발급 재요청은 원래 발급자의 동일한 현재 참여를 요구하며 만료된 원래 링크도 그대로 반환합니다. 참여 재요청은 원래 참여가 계속 유효하면 후속 링크 만료/발급자 이탈과 독립적으로 최초 201/200을 반환하되 현재 역할을 조회합니다. 종료 후 재참여 또는 삭제된 공간을 영수증만으로 복구하지 않습니다.
- 토큰은 `SecureRandom` 32바이트의 Base64URL 값입니다. 조회에는 SHA-256 해시를 사용하고 UNIQUE로 검사합니다. 같은 발급 요청에 원래 URL을 전달하려면 복원이 필요하므로 URL 전체를 AES-256-GCM으로 암호화하여 저장합니다. 매 암호화마다 새 12바이트 nonce, 128비트 인증 태그, invitation ID가 포함된 AAD를 사용하며 저장 형식은 `v1.<Base64(nonce+ciphertext+tag)>`입니다. 토큰 인코딩 길이는 내부 생성 형식이며 별도 제품 입력 정책이 아닙니다.
- `INVITATION_ENCRYPTION_KEY`는 DB 외부의 안정된 32바이트 Base64 키로 `COMMAND_DIGEST_KEY`와 분리합니다. 운영에서는 모든 인스턴스가 같은 비밀값을 사용하고 키를 바꾸기 전에 암호문 이관/키 버전 관리가 필요합니다. local/test의 공개 기본값은 개발 전용입니다. [JDK Cipher의 GCM nonce·AAD 계약](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/javax/crypto/Cipher.html)을 따릅니다.
- `INVITATION_URL_PREFIX`는 미정인 FE 진입 경로를 분리합니다. 원래 URL 전체를 보관하므로 설정 변경이 기존 발급 재응답을 바꾸지 않습니다. 실제 FE 화면·로그인 후 초대 복귀는 별도 연결이 필요합니다. OAuth 성공 경로는 변경하지 않습니다.
- `SpaceMemberQueryService`는 요청자의 현재 참여 권한과 목록을 한 SQL 스냅샷에서 조회합니다. 이름 null 허용, 소유자 우선 정렬을 유지하며 담당 할 일 집계는 CareItem 구현 전에는 추가하지 않습니다.
- 나가기·내보내기·소유권 이전은 아래 참여 변경 흐름에서 처리합니다. 공간 삭제 API와 초대/영수증 정리 보관 정책은 후속 작업입니다. 물리 삭제는 초대↔참여 FK와 원본 삭제 전파를 함께 설계해야 하며 임의 CASCADE나 TTL을 추가하지 않습니다.

### 소유권 이전·참여 종료

`MembershipLifecycleService`는 기존 V3·V4 컬럼과 성공 요청 기록을 사용합니다. 새 마이그레이션이나 형식만 갖춘 CareItem Service는 추가하지 않습니다. 공개 계약은 [참여 변경 API](api-conventions.md#소유권-이전공간-나가기구성원-내보내기-api)를 따릅니다.

- 요청 잠금 → 성공 기록 검증 → 공간/요청자 참여 → 대상 참여 순서로 잠급니다. 최초 실행은 현재 역할과 `expectedSpaceVersion`을 검사하고, 소유권/참여 변경·공간 버전·수정 시각·성공 기록을 함께 커밋합니다. 참여 종료 행을 삭제하지 않습니다.
- 이전의 `owner_membership_id`·`owner_user_id`를 함께 변경하여 역할을 바꿉니다. 별도 역할 행을 복제하지 않습니다. 다른 공간의 동시 생성·이전과 호칭이 충돌하면 기존 UNIQUE 제약으로 전체 롤백하고 `SPACE_LABEL_DUPLICATED`를 반환합니다.
- `TRANSFER_OWNERSHIP`, `DEPART_SPACE`, `REMOVE_MEMBERSHIP`은 `SPACE:<UUID>` 범위를 사용하고 대상 참여/SELF·검토한 버전을 HMAC 입력에 포함합니다. 성공 기록의 actor·종류·대상·처리 시각으로 처리 주체를 추적하며 민감한 공간 내용은 복제하지 않습니다.
- 이전 재전송은 동일한 현재 참여, 내보내기 재전송은 동일한 현재 소유자 참여를 요구합니다. **본인 나가기만** 성공 기록에서 종료 참여 ID·시각을 반환하는 예외입니다. 새 참여를 조회하거나 변경하지 않으므로 재참여 후 재전송도 새 참여를 종료하지 않습니다.
- CareItem의 미완료 담당 해제·잠금 무효화·영향 항목 버전/이력 처리는 아직 없습니다. 해당 도메인 도입 전에 참여 종료 트랜잭션 안에서 Service를 호출하도록 연결해야 합니다. 종료와 담당 해제 중 하나만 커밋하면 안 되며 일반 편집 잠금 때문에 종료를 막지 않습니다.
- Proposal 후속 계약은 새 소유자가 대기 요청을 검토하고, 종료된 참여자의 미처리 요청은 반영을 거절하되 이력을 보존하는 것입니다. 담당 해제·요청 상태를 이번 구현이 완료했다고 간주하지 않습니다. Sharing도 현재 참여 권한을 적용해야 합니다.

### 소식 원본 저장·조회

- V5는 `source_record`를 추가합니다. 공간·작성 당시 참여의 복합 FK, 성공 기록 참조의 UNIQUE, ACTIVE/ERASED 상태 제약을 둡니다. 기존 V1~V4 데이터는 유지하며 적용된 마이그레이션을 수정하지 않습니다. JdbcTemplate 저장 모델을 사용하고 엔티티를 공개 응답으로 노출하지 않습니다.
- 작성은 요청 잠금 → 기존 성공 확인 → 공간/현재 참여 잠금 → 성공 기록·원본 저장 순입니다. 둘 중 하나가 실패하면 함께 롤백합니다. 같은 공간에서 참여 종료와 작성은 기존 공간 잠금 순서를 공유합니다. 원본 저장은 공간 버전·수정 시각을 바꾸지 않습니다.
- `CREATE_SOURCE_RECORD`, `SPACE:<UUID>`와 정규화하지 않은 원문을 HMAC에 포함합니다. 성공 기록에는 원본 ID와 작성 당시 참여 ID만 남깁니다. 재전송은 동일한 현재 참여·활성 공간·ACTIVE 원본을 요구하며 원문을 영수증에 복제하거나 삭제된 원본을 재생성하지 않습니다.
- 조회는 현재 공간/참여 권한과 원본을 하나의 SQL 스냅샷에서 읽습니다. 읽기 경로에는 쓰기용 `CareSpaceAccessService`의 행 잠금을 사용하지 않습니다. 작성자 참여 종료는 원본 삭제가 아니며 `isMine`은 참여 ID가 아닌 동일 회원 기준으로 계산합니다.
- 최신순 커서는 등록 시각·UUID 위치를 사용합니다. 현재 저장은 서버 UTC 마이크로초 시각을 고정합니다. 커서는 공간·위치를 HMAC으로 묶은 불투명 값이며 기존 `COMMAND_DIGEST_KEY`를 별도 용도 식별자와 함께 사용합니다. 새 비밀키나 TTL은 추가하지 않습니다. 키 변경 시 기존 커서는 무효가 되어 첫 목록부터 다시 조회해야 합니다.
- 원본 버전은 1부터 시작합니다. ERD의 삭제 상태·내용 제거 제약과 삭제 원본 조회/재전송 차단은 준비했지만 삭제 API·삭제 영향 확인·파생 내용 제거는 구현하지 않았습니다. 후속 삭제는 같은 공간 잠금 순서를 지켜야 합니다.
- 새 소식은 원본·성공 요청 기록·최초 QUEUED 분석을 같은 트랜잭션에서 저장합니다. 조회의 `latestAnalysis`는 최신 실행 상태이며, 분석 도입 전 원본에는 null을 유지합니다. 원본 수정 API·임시 저장·자동 보관 만료·기존 원본 일괄 분석은 추가하지 않습니다.

## 분석 실행과 제안 저장

v2 실행별 계약 버전·입력 근거 캡처·네 작업의 저장·공개 조회 확장은 [v2 실행 계약](ai-contract-v2-execution.md)을 따른다. 아래 기존 V6~V9 설명 중 CREATE 제한은 v1에 해당한다. V10 이후 제안 상세는 REPEATABLE_READ 스냅샷에서 현재 값과 비교 근거를 함께 확인한다. v2도 최종 반영·CareItem 변경은 수행하지 않는다.


- V6는 `analysis_run`, `analysis_input_source`, `content_document`, `evidence`, `ai_proposal`을 추가합니다. 같은 공간의 복합 FK, 원본별 진행 중 분석 하나, 최초 실행 하나, 성공 실행 하나, 같은 실패의 후속 실행 하나를 DB 제약으로 보장합니다. 성공 재분석은 지원하지 않아 generation 세대는 아직 도입하지 않습니다.
- 소식 생성의 `analysis`는 최초 접수 정보입니다. 같은 생성 요청 재전송은 실행이 끝났어도 원래 ID와 QUEUED를 반환하고 새 분석을 만들지 않습니다. 최신 상태는 조회로 확인합니다. 분석 접수·종료가 원본이나 공간 버전을 올리지는 않습니다.
- 작업을 짧은 트랜잭션에서 점유한 뒤 AI HTTP를 트랜잭션 밖에서 호출합니다. 실행 UUID·lease·생존 갱신으로 소유권을 검사하고 결과 저장 트랜잭션에서 공간·현재 입력 원본/버전·요청 당시 참여 유효성을 다시 검사합니다. 공간 → 실행 행 순으로 잠급니다. 기존 공간 변경·참여 종료도 공간 행 잠금을 공유합니다.
- 요청자의 참여가 끝나면 원본은 유지하고 실행은 FAILED로 종료합니다. 현재 다른 참여자가 실패를 재시도할 수 있습니다. 원본이 삭제·변경되거나 공간이 삭제 중이면 DISCARDED로 처리합니다. lease 만료 실행은 실패로 복구하며 원격 AI 호출의 정확히 한 번 실행을 보장하거나 자동 재전송하지 않습니다.
- 분석 결과의 형식·요청 ID·근거·후보 범위를 검증한 뒤 모든 CREATE 제안과 문서·근거, COMPLETED 상태를 원자적으로 저장합니다. 제안 0개도 성공입니다. 어떤 제안 저장이라도 실패하면 결과 전체를 롤백하고 실패 상태를 별도 트랜잭션에서 기록합니다.
- `analysis_input_source`는 분석에 입력한 모든 원본의 의존 관계입니다. CareItem 후보는 같은 공간의 유효한 문서·근거만 조회하고 후보의 원본 의존성도 등록합니다. V8의 `analysis_input_item`은 후보 항목 버전·문서 ID를 기록하여 결과 저장 시 변경·삭제·문서 제거를 재검증합니다. V9는 분석 시작 당시의 근거 ID 배열을 추가하여 연결·근거 행 삭제 뒤에도 근거 제거를 확인합니다. 인용문은 복사하지 않고, 같은 공간 및 캡처한 원본 버전과의 일치도 검사합니다. 빈 배열은 원본 근거 없음, null은 과거 미기록으로 구분하며 미기록 후보에 의존한 실행은 완료하지 않습니다.
- `AnalysisExecutionService.invalidateSource`는 원본 삭제와 **같은 트랜잭션**에서 호출해야 하는 연결점입니다. 해당 원본을 입력한 모든 실행을 DISCARDED로 만들고 복사한 제안 문서·근거를 null로 제거합니다. 늦은 결과·재전송으로 복원하지 않습니다. 메타데이터만 유지하며 내용 보관 TTL은 정하지 않습니다.
- 제안 물리 저장은 CREATE/OPEN에 한정합니다. CareItem 후보가 전달되어도 UPDATE/RESOLVE는 저장하지 않고 의존성 실패로 처리합니다. 제안 승인·수정·거절과 현재값·이력·공유의 전체 삭제 전파는 후속이며 원본 삭제 공개 API가 완성된 것은 아닙니다.
- 실행기 활성화는 외부 설정으로 선택하며 숫자 기본값은 없습니다. 비활성 환경에서 분석은 QUEUED에 머뭅니다. 자동 테스트는 격리 DB와 가짜 AI를 사용하며 실제 모델 품질을 검증하지 않습니다.

## 제안 조회와 내용 노출 경계

- `ProposalQueryRepository`는 활성 공간·현재 참여·제안·모든 입력 원본 버전·문서/근거의 제거 상태를 하나의 SQL 스냅샷으로 검사합니다. CareItem 후보의 버전·현재 문서·가시성·재확인 상태와 시작 시 기록한 근거 ID도 재검증합니다. 무효 의존성은 저장 내용이 남아 있어도 응답에서 숨기며 조회로 상태를 변경하지 않습니다. 빈 페이지에도 권한 검사를 적용하고 쓰기용 공간 행 잠금을 획득하지 않습니다. V7은 `(space_id, created_at DESC, id DESC)` 인덱스만 추가합니다.
- 저장된 CREATE/OPEN을 공개 `CREATE_ITEM/REVIEW_PENDING`으로 변환합니다. 원본 삭제/버전 변경, 실행 폐기, 문서·근거 제거는 `INVALIDATED`로 보이며 기본 목록에서 제외합니다. GET에서 이를 DB에 기록하거나 삭제를 실행하지 않습니다.
- 유효성 검사에는 주 원본뿐 아니라 `analysis_input_source`의 모든 원본을 포함합니다. 아직 물리 삭제 전파를 호출하지 않은 상태도 SQL의 CASE로 제목·문서·인용문·작성자 정보를 읽기 결과에서 제거합니다. 이 방어는 원본 삭제 트랜잭션의 실제 파생 내용 제거를 대체하지 않습니다.
- 생성 시각·ID로 정렬하고 필터·공간·위치를 기존 HMAC 키의 `PROPOSAL_CURSOR` 용도로 묶습니다. 커서는 권한이나 고정 스냅샷이 아니며 매 요청 현재 참여를 재확인합니다. 새 제안은 첫 페이지 재조회로 확인합니다. TTL이나 새로운 비밀키는 추가하지 않습니다.
- `ProposalValueMapper`는 내부 문서에서 유형별 공개 조회 DTO로 허용한 값만 변환합니다. 내부 AI DTO/`changes`를 그대로 노출하거나 관리 항목에 반영하지 않습니다. 담당자 ID는 동일 공간의 현재 참여일 때만 반환합니다. 원본 작성자의 참여 종료는 완료 제안을 제거하지 않으며 회원 연결이 제거되면 작성자는 탈퇴 표시로 익명화합니다.
- 현재 CREATE에는 비교 대상·현재 값·버전이 없습니다. 후보 배열은 비어 있고 reviewToken은 발급하지 않습니다. 관계·상충 판정 계약도 연결되지 않아 null입니다. CareItem·승인 API를 도입할 때 실제 후보·잠금·버전 재검사·원자적 반영을 연결해야 합니다.

### OAuth 회원 매핑

- `global.security.oauth`는 Spring Security의 기본 Google OIDC·Kakao OAuth2 사용자 조회/검증을 위임하고, 검증된 제공자 식별자를 `user.service.SocialLoginMemberService`로 전달합니다. 제공자 HTTP 통신 동안 회원 DB 트랜잭션을 열어두지 않습니다.
- 식별 기준은 Google ID Token의 `sub`, Kakao의 정수 `id`와 제공자 구분입니다. 이메일·표시 이름으로 계정을 연결하지 않습니다.
- 회원 조회/생성은 `READ_COMMITTED` 트랜잭션에서 제공자 식별자별 `pg_advisory_xact_lock`을 획득한 뒤 수행합니다. 잠금은 같은 DB를 사용하는 여러 서버에서도 적용되고 커밋/롤백 때 해제됩니다. 해시 충돌은 처리 순서에만 영향을 주며 실제 조회·유일성 검사는 전체 `(provider, provider_user_id)`로 수행합니다. 관련 생성 경로는 이 서비스를 사용해야 합니다.
- 최초 가입에서만 제공자 이름을 저장하고 이름이 없으면 null을 허용합니다. 재로그인은 기존 이름과 `updated_at`을 유지합니다(2026-10-09 사용자 합의). 별도 이름 수정 정책은 미정입니다.
- 회원과 소셜 연결 생성은 전체 성공 또는 전체 롤백입니다. DB 실패는 기존 로그인 실패 응답으로 변환하며 SQL 파라미터·제공자 원문을 응답에 포함하지 않습니다.
- 로그인 성공 시 `MemberPrincipal`에 서비스 사용자 UUID를 연결하고 인증 이름도 UUID로 사용합니다. Google은 `OidcUser` 형식과 검증 결과를 유지하며 두 제공자 모두 JDBC 세션 저장·복원 후 같은 회원을 식별합니다. 기존 제공자 전용 세션은 자동 변환하지 않고 재로그인을 요구합니다.
- 로그인한 회원이 필요한 업무 Controller는 `@CurrentUser AuthenticatedUser`를 사용합니다. `global.security.CurrentUserArgumentResolver`가 인증된 `MemberPrincipal`을 확인하고, `user.service.MemberIdentityService`가 UUID·제공자·제공자 사용자 ID에 대응하는 현재 DB 연결을 검증합니다. 사용자 FK로 회원 존재를 보장하며 없는 회원·끊어진 연결·UUID 불일치는 `401 UNAUTHENTICATED`입니다. DB 장애는 `500 INTERNAL_ERROR`이며 두 경우 모두 Controller의 업무 메서드를 호출하지 않습니다.
- `global.config.WebMvcConfig`가 공통 처리기를 MVC에 등록합니다. 요청에서 사용자 ID를 바인딩하지 않고 검증된 UUID만 Controller에 전달하며 엔티티·제공자 정보는 노출하지 않습니다. 검증은 요청마다 수행하되 공개 API에는 일괄 적용하지 않습니다. Security 필터의 경로 접근·CSRF 검사와 각 도메인 Service의 공간 참여·권한 검사는 별도로 유지합니다.
- `GET /api/users/me`는 공통 회원 검증 후 `UserProfileService`에서 현재 DB의 이름·연결된 제공자만 공개 DTO로 반환합니다. 사용자 ID를 입력받거나 전역 공간 역할을 반환하지 않습니다. 조회는 회원·연결을 생성하지 않으며, 조회 시점에 회원이 사라졌다면 `401 UNAUTHENTICATED`입니다. URL·응답 필드·세션 쿠키 계약은 그대로 유지합니다.
- 실제 제공자 로그인 검증과 가짜 제공자 기반 자동 검증을 구분합니다. 회원 탈퇴 시 모든 세션 종료와 소유권 검사는 후속 구현 범위입니다.

구현 참고: [Spring Security 사용자 서비스 확장](https://docs.spring.io/spring-security/reference/servlet/oauth2/login/advanced.html), [PostgreSQL 트랜잭션 advisory lock](https://www.postgresql.org/docs/17/explicit-locking.html#ADVISORY-LOCKS), [Google 식별자](https://developers.google.com/identity/openid-connect/openid-connect), [Kakao 사용자 정보](https://developers.kakao.com/docs/ko/kakaologin/rest-api#req-user-info).

## 운영 기준

- 개발: 로컬 Java·Python 프로세스와 Docker PostgreSQL
- 초기 배포: 외부 LLM API를 사용하는 소규모 MVP, Lightsail Linux 2 vCPU·4GB급에서 시작
- Nginx를 통해 동일 도메인·HTTPS 제공, Spring·AI·DB 내부 통신
- 운영 DB 비밀값은 환경변수로 주입하고 DB 백업은 별도 저장소에 보관
- 단일 서버 장애 시 전체 서비스가 중단될 수 있으므로 실제 이용 규모에 맞춰 DB·애플리케이션 분리 검토
- 합성 기록으로 먼저 검증하고, 실제 부모님 정보를 사용하기 전 동의·열람 범위·공유 내용·데이터 보관 정책 구체화

Redis, 벡터 DB, Spring AI, 메시지 브로커는 초기 의존성에 포함하지 않습니다. 실제 요구와 측정 결과에 따라 도입합니다.
