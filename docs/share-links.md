# 공유 링크

현재 참여자가 확정 항목을 선택해 링크를 발급하고, 링크를 연 현재 참여자가 최신 내용을 조회하는 계약이다. 링크는 초대나 권한 부여가 아니며 자동 만료는 없다. 카카오 SDK·메시지 전송·링크 해제 API·로그인 후 복귀·FE 진입 화면은 후속 범위다.

## 발급

`POST /api/spaces/{spaceId}/share-links`는 로그인 세션과 CSRF가 필요하다. 현재 소유자와 구성원 모두 사용할 수 있으며 편집 잠금은 필요하지 않다.

```json
{
  "clientRequestId": "11111111-1111-4111-8111-111111111111",
  "targets": [
    {
      "itemId": "22222222-2222-4222-8222-222222222222",
      "expectedItemVersion": "3",
      "includesChange": true
    }
  ]
}
```

- 대상은 하나 이상이며 같은 항목을 중복 선택할 수 없다. 합의되지 않은 최대 선택 개수는 추가하지 않는다. 원시 요청 본문의 기술적 상한은 기존 변경 API와 같은 1 MiB이며 청크 요청에도 적용한다.
- 버전은 1~9223372036854775807의 십진 정수 **문자열**, 변경 표시는 불리언이다. 누락·형 변환·정의되지 않은 필드는 허용하지 않는다.
- 같은 공간의 현재 유효한 확정 항목 전체를 검사한 뒤 하나의 링크로 저장한다. 삭제·재확인·문서 제거 항목, 대기 제안·변경 요청은 새 공유 대상이 될 수 없다. 유형은 일정·할 일·질문·관찰·안내이며 완료·취소 일정도 공유할 수 있다.
- `includesChange`는 변경 안내로 공유하려는 선택이다. `true`는 서버에서 생성 이후의 유효한 확정 변경 이력을 확인해야 한다. 버전 증가만으로 인정하지 않으며 현재 버전 이하의 읽을 수 있는 UPDATE·RESOLVE·LINK_EVIDENCE·UNASSIGN·RECONFIRM 이력을 확인한다. 변경 이력이 있어도 일반 공유는 `false`로 선택할 수 있다.
- 요청 잠금 → 현재 공간·참여 잠금 → 전체 대상 검증 → 링크·대상·영수증 저장을 한 트랜잭션으로 처리한다. 원본 삭제·일반 삭제·항목 변경·참여 종료와 공간 행 잠금을 공유하며 부분 발급하지 않는다. 항목·공간 버전과 수정 시각은 변경하지 않는다.

성공은 201과 공통 `ApiResponse`이며 `data`는 다음 형태다. 모든 카드의 URL은 같은 복수 대상 링크다. 카드에는 유형·변경 표시·서비스 URL만 포함하며 부모님 호칭, 제목, 증상, 병원, 날짜, 담당자, 원문·인용·돌봄 본문은 포함하지 않는다.

```json
{
  "shareLinkId": "33333333-3333-4333-8333-333333333333",
  "shareUrl": "https://hanmaum.site/share/<opaque-token>",
  "cards": [
    {
      "itemType": "SCHEDULE",
      "includesChange": true,
      "url": "https://hanmaum.site/share/<opaque-token>"
    }
  ]
}
```

동일 회원·요청 ID·공간·순서 있는 대상·버전·변경 표시의 재전송은 최초 URL과 최소 카드 정보를 201로 반환한다. 요청 의도가 다르면 `IDEMPOTENCY_KEY_REUSED`다. 재전송에도 현재 활성 공간·참여와 발급 당시 참여 ID를 확인한다. 탈퇴 후 새 참여로 재가입하면 이전 발급 요청을 재전송할 수 없다. 최초 발급 이후 항목이 바뀌거나 삭제되어도 안전한 최초 카드 메타데이터만 재전달하며, 링크를 열 때는 항상 현재 상태를 조회한다. 재전송은 새 링크 생성이나 과거 내용 복원이 아니다.

## 조회

`GET /api/share-links/{token}`은 로그인 세션이 필요하고 CSRF는 필요하지 않다. 성공은 200과 공통 `ApiResponse`다.

```json
{
  "spaceId": "44444444-4444-4444-8444-444444444444",
  "items": [
    {"itemId": "22222222-2222-4222-8222-222222222222", "state": "AVAILABLE", "item": {}},
    {"itemId": "55555555-5555-4555-8555-555555555555", "state": "NEEDS_RECONFIRMATION", "item": null},
    {"itemId": "66666666-6666-4666-8666-666666666666", "state": "DELETED", "item": null}
  ]
}
```

예제의 AVAILABLE `item`에는 기존 항목 상세 I02와 같은 **최신 `CareItemDetail`**이 들어간다. 발급 버전의 과거 스냅샷을 조회하지 않는다. 선택 순서를 보존하고 전체 응답을 하나의 REPEATABLE READ 스냅샷으로 조회하므로 동시에 변경되는 항목·권한·원본 제거 상태를 섞지 않는다.

- 삭제 항목은 `DELETED`, 재확인 필요 또는 현재 문서를 읽을 수 없는 항목은 `NEEDS_RECONFIRMATION`이다. 둘 다 `item: null`로 반환하며 일부 독립 필드가 남아 있어도 본문을 반환하지 않는다. 일반 삭제는 보존된 이력을 공유로 노출하지 않는다.
- 원본 삭제 직후 기존 링크에도 제거 상태가 적용된다. 소유자가 새 근거로 재확인하면 새로 확정된 현재 내용만 다시 조회할 수 있다.
- 링크 발급자가 나가더라도 다른 현재 참여자는 계속 조회할 수 있다. 나간 발급자는 403이며, 나중에 새 참여로 재가입하면 현재 참여 권한으로 조회할 수 있다. 기존 발급 영수증 재전송과는 별개다.
- 미로그인은 401, 비참여자·나간 구성원은 403이다. 오류에는 공간 호칭·항목 내용·토큰을 넣지 않는다. 링크 형식 오류·없는 링크·비활성/없는 공간·대상 식별 정보가 전부 제거된 링크는 404다.
- 두 API 모두 `Cache-Control: no-store`다. 외부 카드나 링크 자체만으로 익명 미리보기·답변·해결 처리 권한이 생기지 않는다.

## 오류

| HTTP | 코드 | 조건 |
| --- | --- | --- |
| 400 | `INVALID_REQUEST` | 필드·UUID·버전·불리언 형식, 빈/중복 대상 |
| 401 | `UNAUTHENTICATED` | 로그인 없음/유효 회원 연결 없음 |
| 403 | `FORBIDDEN` | CSRF 오류, 현재 참여 아님, 재전송의 원래 참여 종료 |
| 404 | `RESOURCE_NOT_FOUND` | 없는/다른 공간의 대상, 유효하지 않은 링크, 비활성 공간 |
| 409 | `VERSION_CONFLICT` | 신규 발급 대상의 현재 버전 불일치 |
| 409 | `SHARE_TARGET_UNAVAILABLE` | 삭제·재확인 대상 또는 변경 표시의 유효한 확정 변경 없음 |
| 409 | `IDEMPOTENCY_KEY_REUSED` | 같은 요청 ID의 다른 업무·공간·대상·순서·버전·변경 표시 |
| 409 | `REQUEST_IN_PROGRESS` | 같은 회원·요청 ID가 다른 트랜잭션에서 처리 중 |
| 413 | `PAYLOAD_TOO_LARGE` | 원시 요청 본문 1 MiB 초과 |

## 저장·설정·연동

V21은 `share_link`, `share_link_target`만 추가한다. 링크에는 ID·공간·발급 당시 참여·토큰 SHA-256 해시·원래 URL 접두사·발급 시각을 저장하고, 대상에는 순서·항목 ID·유형·발급 버전·변경 표시만 저장한다. 문서 본문·근거·원문·제목 스냅샷과 원문 토큰은 저장하지 않는다. 영수증 결과는 링크 ID와 참여 ID뿐이다. 복합 FK로 링크·항목·발급 참여가 같은 공간인지 보장한다. 기존 Flyway·문서·항목은 변경하지 않는다.

토큰은 임의 서버 링크 UUID와 공간 UUID를 `COMMAND_DIGEST_KEY`로 HMAC-SHA256 처리하되 `HANMAUM_SHARE_LINK_TOKEN_V1` 도메인으로 분리한 43자 Base64URL 값이다. 원래 URL 접두사를 함께 보존하므로 설정 변경 후에도 동일 요청의 URL을 재구성할 수 있다. **재전송 가능한 공유 링크가 남아 있는 동안 같은 키를 모든 인스턴스·재시작에서 유지해야 한다.** 기존 [배포 키 비교](../deploy/release_env.py)의 `STABLE_NAMES`에 이 키가 포함되어 있으며, `activate-release.sh`는 저장된 기준과 다른 키의 일반 배포를 거부한다. 이 동작은 기존 `deploy/tests/test_release.py`에서 검증한다. 키 교체가 필요하면 기존 영수증과 공유 URL 재전달을 포함한 별도 이행 계획이 필요하며, 이번 범위에서 임의 회전·다중 키 운영을 지원하지 않는다. 키 불일치 시 재전달은 실패하며 새 URL을 대신 발급하지 않는다. 이미 전달된 URL의 조회는 저장된 해시로 처리하므로 키 교체만으로 기존 링크가 해제되지는 않는다.

`app.sharing.url-prefix`는 `SHARE_URL_PREFIX`로 설정하며 사용자 입력 URL은 받지 않는다. 인증 정보·쿼리·fragment가 없는 `/`로 끝나는 절대 HTTP(S) URL이어야 한다. local·prod 기본값은 기존 `FRONTEND_URL` 뒤 `/share/`이며 로컬은 `http://localhost:5173/share/`다. 현재 운영 Compose의 `FRONTEND_URL`로는 `https://hanmaum.site/share/`가 된다. 별도 신규 Secret이나 카카오 키는 필요하지 않다. 운영 진입 경로를 바꾸려면 배포 환경 전달 설정도 함께 조정한다.

FE는 이 URL을 받을 경로와 로그인 후 복귀를 연결한 뒤 실제 공유를 제공해야 한다. 현재 BE 작업만으로 해당 FE 화면이나 카카오 발송이 구현된 것은 아니다. 기존 외부 발송 카드를 회수할 수 있다고 표시하지 않는다. 공통 handoff·Notion 최종 동기화는 별도 요청 시 진행한다.
