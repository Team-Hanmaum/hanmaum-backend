# 공간 전체 삭제

현재 소유자가 삭제 영향을 확인한 뒤 공간과 소속 서비스 데이터를 한 트랜잭션에서 제거한다. 일반 항목 숨김·소식 원본의 내용 제거·공간 나가기와 다른 작업이며 MVP 복구는 제공하지 않는다. 삭제/무효 상태를 포함한 전체 집계, 동기 삭제 완료 후 200, 삭제 후 동일 요청 404는 사용자 확인 기준이다.

## 영향 확인

`GET /api/spaces/{spaceId}/deletion-impact`는 로그인한 **현재 소유자**만 호출할 수 있다. CSRF는 필요하지 않으며 성공은 200과 공통 `ApiResponse`다.

```json
{
  "spaceId": "11111111-1111-4111-8111-111111111111",
  "spaceVersion": "3",
  "counts": {
    "members": 3,
    "records": 5,
    "items": 8,
    "proposals": 4,
    "requests": 2,
    "historyEntries": 12
  },
  "impactToken": "<64자리 소문자 hex 영향 확인값>"
}
```

위 예제는 `data` 내부다. 공간 호칭·가족 이름·소식·항목 제목·본문·인용은 반환하지 않는다. 집계는 다음 테이블의 전체 행 기준이다.

| 필드 | 집계 |
| --- | --- |
| members | `space_membership`: 현재/종료 참여 모두 포함, 사용자 수가 아닌 참여 행 수 |
| records | `source_record`: ACTIVE/ERASED 모두 포함 |
| items | `care_item`: 일반 삭제·재확인 항목 포함 |
| proposals | `ai_proposal`: 반영·미적용·무효 제안 포함 |
| requests | `change_request`: 요청 제출 묶음 수, 항목 수가 아님 |
| historyEntries | `care_item_history`: 관리 항목 확정 변경 이력 수 |

화면의 여섯 집계만으로 영향이 같다고 판단하지 않는다. 공간·참여·원본·분석·입력 의존성·문서·근거·항목·제안·승인 결과·변경 요청·잠금·초대·공유까지 24개 소속 테이블의 정렬된 메타데이터를 같은 REPEATABLE READ 스냅샷에서 읽는다. HMAC은 도메인(`care-space-deletion-impact:v1`)·사용자·공간·공간 버전·테이블 구분·행 수·행 상태에 결합한다. 본문·호칭·인용·암호화 URL·URL 접두사·토큰 관련 값은 메타데이터에서 제외하고 처리 기록에도 복사하지 않는다.

문서 내용 변경은 기존의 불변 문서/새 문서 ID·버전 규칙을 따르고, 내용 제거는 상태·제거 시각·버전에 반영된다. 단순 잠금/분석 lease 기한 갱신과 초대 만료 시각은 삭제 범위를 바꾸지 않아 확인값에서 제외한다. 새로운 소식·근거·문서·요청·초대·공유나 상태/연결 변경은 건수가 같거나 공간 버전이 같아도 확인값을 바꾼다. 별도 토큰 TTL은 추가하지 않는다. 영향 확인 자체는 업무 데이터를 변경하지 않는다.

## 삭제 실행

`POST /api/spaces/{spaceId}/deletions`는 로그인한 현재 소유자와 CSRF가 필요하다. 편집 잠금을 요구하지 않으며 다른 가족이 보유한 잠금도 삭제 대상이다.

```json
{
  "expectedSpaceVersion": "3",
  "impactToken": "<영향 확인 응답의 확인값>",
  "clientRequestId": "22222222-2222-4222-8222-222222222222"
}
```

- 세 필드는 필수다. 버전은 1~9223372036854775807의 십진 정수 **문자열**, 요청 ID는 UUID, 확인값은 64자리 소문자 hex다. 형 변환·정의되지 않은 필드는 허용하지 않는다. 원시 본문은 기존 변경 API와 같은 기술적 상한 1 MiB를 적용한다.
- 요청 ID 잠금 → 성공 영수증 비교 → 현재 소유자·공간 행 잠금 → 공간 버전 → 최신 영향 그래프 비교 → 소속 데이터 제거 → 최소 성공 영수증 저장 순서다.
- 전체 삭제와 다른 소속 변경은 같은 공간 행 잠금으로 직렬화한다. 확인 이후 소식·제안·근거·공유 등이 바뀌면 삭제하지 않고 `DELETION_IMPACT_CHANGED`를 반환한다. 소유권·참여·공간 정보 변경도 현재 권한·버전으로 다시 검사한다.
- 먼저 트랜잭션 내부에서 `DELETING`으로 전환하고, FK의 자식→부모 순서로 항목·근거·문서·원본·분석·이력·제안·요청·초대·공유·참여와 공간을 물리 삭제한다. 초대/참여의 순환 참조는 참여의 초대 참조를 해제한 뒤 제거한다. 기존 지연 소유자 FK를 포함해 제약을 끄지 않는다.
- 서비스 데이터와 성공 기록이 모두 커밋된 뒤 200을 반환한다. 중간 오류는 전부 롤백되어 원래 활성 공간·원본·문서·링크 등을 유지한다. 완료되지 않은 정리를 성공이나 202로 반환하지 않는다.

성공 `data`는 다음 두 필드뿐이다.

```json
{
  "spaceId": "11111111-1111-4111-8111-111111111111",
  "deletedAt": "2026-11-07T13:00:00Z"
}
```

영향 확인과 삭제 성공 모두 `Cache-Control: no-store`다.

## 재전송·동시 실행·AI 결과

- 삭제 완료 뒤 **동일한 성공 삭제 요청**도 404다. 성공 응답이 유실됐더라도 404만으로 원래 요청 실패를 단정하거나 새 요청 ID로 공간을 복구하지 않는다. FE는 참여 공간 목록을 다시 조회한다.
- 처리 중 동일 사용자·요청 ID 충돌은 `REQUEST_IN_PROGRESS`, 동일 ID를 다른 작업·대상·버전·확인값에 사용하면 `IDEMPOTENCY_KEY_REUSED`다. 다른 ID로 동시에 삭제하면 하나만 성공하고, 나머지는 공간이 사라져 404가 된다.
- 전역 `command_receipt`는 공간 FK를 가진 돌봄 자료가 아니다. 기존 최소 ID·버전·시각·요청 HMAC 기록을 보존해 과거 공간 생성·작성·발급 요청이 새 작업으로 실행되는 것을 막는다. 신규 삭제 영수증의 결과는 `deletedAt`뿐이며 원문·호칭·제목·영향 토큰·전체 응답은 저장하지 않는다. 별도 명령 결과 조회 API나 새로운 보관 TTL은 추가하지 않는다.
- 삭제한 호칭으로 **새 요청**을 사용한 별도 공간 생성은 가능하다. 기존 공간 생성 요청을 재전송하면 기존 ID에 대한 접근이 404가 되며 새 공간을 만들지 않는다.
- 기존 초대는 기존 `404 INVITATION_UNAVAILABLE`, 공유와 소속 자료는 `404 RESOURCE_NOT_FOUND` 등 해당 API의 기존 오류 계약에 따라 차단된다. 과거 초대 참여 성공 요청이나 편집 잠금·승인 요청·분석 재시도로 공간을 되살릴 수 없다. 나가기 등 기존에 합의된 최소 결과 재응답 예외는 해당 도메인의 계약을 유지한다.
- 분석 작업·입력 의존성도 제거한다. 삭제 후 또는 삭제 트랜잭션 뒤에서 기다리던 v1/v2 분석 완료는 사라진 실행을 안전하게 폐기(`false`)하고 제안·근거를 저장하지 않는다. heartbeat·복구·실패 처리도 사라진 실행을 되살리지 않는다. 이미 외부로 전송 중인 HTTP 요청을 소급 취소하거나 제공자 보관 데이터를 제거했다고 주장하지 않는다.

## 오류

| HTTP | 코드 | 조건 |
| --- | --- | --- |
| 400 | `INVALID_REQUEST` | 필수 필드·UUID·버전·확인값 형식, 정의되지 않은 필드 |
| 401 | `UNAUTHENTICATED` | 유효한 로그인·회원 연결 없음 |
| 403 | `FORBIDDEN` | 현재 소유자 아님 또는 CSRF 오류 |
| 404 | `RESOURCE_NOT_FOUND` | 없는/삭제 중/삭제 완료 공간 또는 동일 성공 삭제 재요청 |
| 409 | `VERSION_CONFLICT` | 현재 공간 버전 불일치 |
| 409 | `DELETION_IMPACT_CHANGED` | 영향 범위·상태·사용자·공간 결합 확인값 불일치 |
| 409 | `IDEMPOTENCY_KEY_REUSED` | 같은 요청 ID의 업무·대상·내용 변경 |
| 409 | `REQUEST_IN_PROGRESS` | 같은 사용자·요청 ID 처리 중 |
| 413 | `PAYLOAD_TOO_LARGE` | 원시 본문 1 MiB 초과 |
| 500 | `INTERNAL_ERROR` | 내부 오류. 미완료 삭제 전부 롤백 |

오류에 호칭·본문·토큰·내부 DB 오류를 포함하지 않는다. 일반 구성원에게 영향 집계도 공개하지 않는다.

## 저장 구조·연동 범위

V1~V21을 수정하지 않고 기존 FK와 저장 구조를 사용한다. 새 Flyway/테이블·비동기 worker·임의 상태/TTL은 필요하지 않다. 새 공간 소속 테이블이나 내용 변경 방식이 추가되면 삭제 순서·영향 그래프·전체 테이블 제거 통합 테스트를 함께 갱신한다. 검증은 Testcontainers의 격리 PostgreSQL에서 수행하며 실제 개발/운영 공간을 삭제하지 않는다.

다른 공간, 서비스 회원·소셜 연결·인증 세션은 유지한다. FE는 삭제 범위·복구 불가 안내 후 `impactToken`을 전달하고, 성공 또는 삭제 상태 확인 시 공간과 파생 데이터 캐시를 제거해 참여 공간 목록을 갱신한다. 새 소유자나 영향 범위 변경 오류에서는 새 정보를 확인받아야 하며 버전/토큰만 자동 교체해 재삭제하지 않는다.

이번 완료 범위는 BE 서비스 데이터다. 현재 메타데이터 정렬·JVM 전송량과 공간 잠금 유지 비용은 행 수에 비례한다. 대규모 공간의 실측 후 DB 측 digest 집계나 비동기 삭제를 검토하며, 이번 동기 MVP에 임의 건수 제한을 추가하지 않는다. 대규모 비동기 삭제·중간 작업 복구, 백업/로그/검색 인덱스·AI 제공자 측 보관 자료의 삭제 시점과 복원 시 삭제 재적용은 별도 운영 설계 범위다. FE 화면·공통 handoff·Notion 최종 동기화는 후속 요청 시 진행한다.
